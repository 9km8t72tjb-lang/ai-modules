# Ship agent_spinner's review and repair recipes

## Goal

An orchestrator whose ask is a source-fidelity review, a drift repair across many artifacts, or a read-only audit sweep finds a matching recipe under `plugins/ai_dev/skills/agent_spinner/references/recipes/`. It reads that recipe in full, names it in the run's opening sentence, and follows its phases, orchestrator steps, and checks.

This task ships three recipe files, `fidelity-review.md`, `artifact-repair.md`, and `check-only-audit.md`, with their rows in the `<selector>` recipe table. It also ships the per-recipe static checks that every recipe file must pass, one eval per recipe, and the eval that tests whether an attached skill body leads the orchestrator to read a recipe.

  - [The routing task](ai-dev_agent-spinner-routing.md) ships the recipe table's frame inside `<selector>`. It routes an ask to a recipe only after the ask matched the recipe's shape, and it adds the static check that matches table rows to recipe files one to one.

## Approach

### Recipe file layout

Write each recipe as one file under `references/recipes/`, in pseudo-XML with positive, action-oriented wording, as the standing repo rules require.

- Open with an H1 that names the recipe id and title, such as `# J1. Source-fidelity review and fix`, so a cross-reference by id resolves by search.
- Wrap the body in one outer tag named after the file stem with hyphens turned into underscores, such as `<fidelity_review>`. Inside it, place thirteen field tags in this order: `<trigger>`, `<ledger_steps>`, `<phases>`, `<width>`, `<roles_and_returns>`, `<adversarial_checks>`, `<orchestrator_gates>`, `<failure_handling>`, `<stop_and_ask>`, `<report>`, `<cost_profile>`, `<tier_notes>`, `<post_run_checks>`. A variant ships as its own tag inside the same outer tag.
- List two to four numbered helper phases in `<phases>`. Each phase is one verb plus one clause naming what a helper does over which unit, and it names the earlier returns it reads.
- List the orchestrator steps under `<orchestrator_gates>` in run order. Scouting, calibration with the user, deterministic gates, merges by script, validation, and reporting are orchestrator steps, and so is a single helper dispatched at a barrier, such as a critic, a planner, or a validator. The one repair round re-enters the write and check phases and adds no phase.
- Cite run-protocol steps and checks by their labels, P1 to P6 and C1 to C10. Name ledger verbs and flags only from the frozen set in run-protocol.md's command reference.
- Keep each recipe file at most 12,288 bytes. A matched recipe is read in full and must carry every rule, and the context estimate that P1 requires already counts that load. No standing repo rule caps a reference file, so this one limit covers every recipe, and each planned recipe fits it with all its fields.
- Write rules only. Leave out session figures, cost observations, case evidence, harness product names, tool identifiers, harness paths, instruction-file names, and precedence phrases such as "takes precedence".
- Keep every phase and orchestrator-step label this task names, since the evidence page's step map keys on them.

### Lines every recipe carries

- `<trigger>`: "It runs under {shape} and applies only after the selector matched that shape."
- `<width>`: "A run whose context estimate crosses half the host's window spans sessions at wave ends (P1)."
- `<roles_and_returns>`: "A role barred from file writes returns in its final message, which you relay verbatim to `accept --stdin`, never through a shell (P3)."
- `<orchestrator_gates>` opens with "These orchestrator steps run in this order, and the announcement lists them as checks." Its first step runs the gate-scope check from run-protocol.md's run-directory section before dispatch. A report step builds the report from the ledger after a clean `close` (P6).
- `<failure_handling>`: "At a turn end with rows out, send the interim report. Any later turn runs `status`, then `attach` when a run is open, and accepts every pending return before it continues (P4)."
- `<stop_and_ask>`: "Ask about scope and the estimate before dispatch, with the estimate beside any size guideline the host or user states, and ask before any widening past the enumerated list. An answer the request states is the user's answer. On a host with no later turn, an unanswered gate ends the run with its decision packet (P1). Create the stop file with `stop` the moment a pause request arrives, before any question (P4)."
- `<cost_profile>` opens with "Keep these whatever else is cut: coverage by construction, a review of every landed write, and baseline-differential gates. Offer each cut only as a narrowing the user chooses, with the checks it drops. Estimate the cost as rows per phase, times the per-row cost the pilot measured, plus the checking share." The recipe's own cuts follow.
- `<tier_notes>` holds one note per row of run-protocol.md's tier table: the inline floor, batch delivery, and notice delivery. Each note says only what the orchestrator does differently there and states no host behaviour and no measurement. The block closes with "Headless workers are not available in this version."
- A recipe with a repair round also carries three lines. `<orchestrator_gates>` says "The one repair round (C5) re-enters the write and check phases for the failing rows." `<report>` says "Report each repaired item as re-checked once, recall-limited, and unverified end to end, or as failed after repair (C5)." `<post_run_checks>` says "Each repaired item has exactly one re-check row, at no lower depth than its first check."
- A line that applies a proposal another reference owns stays only while that reference still carries it. These are the half-window session boundary in P1, the sampled unverified band and the known-false control in C7, and the critic's surplus read in C6.

### `fidelity-review.md`: J1, source-fidelity review and fix

- **Trigger.** Per-artifact fan-out. The ask checks derived documents against the sources they cite for dropped details, misreadings, overcompression, invented forks, wrong connections, and missed integration. The run fixes what the sources settle and puts the rest to the user. Signals are pages with a source-lineage field, source captures with recorded content hashes, an index and a log, and live originals behind the captures.
- **Ledger steps.** `init` takes the lineage inventory, its exclusions, and the pages and captures the owning family reports as marked (C9). `accept` checks each finder's coverage list against its unit's recorded inputs. `rows --from-records` creates the Verify rows, `--from-gaps` the gap-unit rows, and `--from-repair-list` the repair rows. Accept the plan against every target path the surviving findings name. The linter differential runs last as a `gate`, and before `close` each changed marked path has a hand-off or fork row.
- **Phases.** **Find**: a read-only finder reads each unit against its cited sources and reads no earlier return. **Verify**: two refute-by-default lenses test each write-bound finding, reading the Find return that raised it. **Write**: a writer applies each target path's confirmed block, reading the findings file. **Review**: a read-only reviewer reads each changed path's diff against the baseline, with its Write return.
- **Width.** One finder per unit row. Verifiers take the write-bound findings plus a fixed sample of each unverified band, times two lenses, in batches of at most five; the sample is a proposal (C7). One writer per target path. One reviewer per changed path in the net diff, the orchestrator's own edits and the index included (C1). One repairer and one re-checker per failing path. The plan caps the gap units. Verify, gap-unit, and repair rows come from accepted records (P4). Lenses and reviewers run no shallower than the passes they check.
- **Roles and returns.** Writers, repairers, and the validator write return files. The finder returns its label, its unit, and findings. Each finding carries an id, a kind (dropped detail, misread, overcompressed, false fork, integration hole, or wrong connection), a severity, a class (fix or decide), the page path and quote, the source path, anchor, and quote, and a suggested fix. The finder also returns its coverage per path (read in full, searched, or unreachable), what it examined and cleared, beyond-brief finds, and incidents. The source lens re-reads the source in context, and the page lens re-reads the page and searches the corpus. Each lens returns, per finding, a verdict (confirmed, partly, or refuted), a corrected statement for partly, the settling span, and a confidence. The writer re-reads the cited source and applies exactly its block. It returns applied, rejected, or routed per finding with the span it re-read, plus contradictions between its instructions and the source, the recorded decisions it touched, and incidents. The reviewer returns issues with a kind (instruction unapplied, unsupported, lost qualifier, dropped content, misquote, decision changed, or prose), a severity, the hunk, the source span, and a fix, plus the hunks it cleared. The repairer re-derives each issue and returns applied, refuted with its span, or routed (C5). The validator returns the invariants held, the invariants broken with path and anchor, and the proposals it left unapplied.
- **Adversarial checks.** Both lenses open from "refuted unless the evidence confirms". A partly verdict's corrected statement replaces the finding downstream. A finding survives when no lens refutes it and at least one lens returns, and it takes the lower severity. When both lenses saw it, its label is "survived both lenses, recall-confirmed". Each batch set carries one known-false control, a proposal (C7). The reviewer opens from the position that the edit dropped, distorted, or skipped something. It reads the diff, the writer's block, and the cited sources, and it clears a hunk only with a hunk citation plus a source citation.
- **Orchestrator gates, in run order.** **Scout**, before Find: build the inventory by script from the lineage fields, and exclude each page with no resolvable source, with its reason. Cut units one helper can read in full, and add the cross-cutting sweeps the corpus needs: a fact ledger, the open questions the sources settle, and sources no capture holds. Run the gate-scope check, record the baseline and the roster (P1), and put the scope forks, the verification scope, and the estimate to the user (C7). When no family owns the corpus, the scout records the corpus's own markers (capture hashes, audit baselines, index and log entries) at `init` as marked targets. **Critic**, at the Find barrier: the completeness critic reads the coverage records, and its gap units become Find and Verify rows (C6). **Findings file**, before Write: build it by script with one block per target path. Use a planner only where root-cause clustering needs judgement, take its plan as a manifest, and treat any canonical statement it writes as a produced artifact (P3). **Repair round**, after Review, for the paths with a blocking or should-fix issue. **Terminal validation**: the validator checks the index, log, and schema invariants. **Hand-offs**: capture hashes, the audit baseline, and index and log upkeep go to the owning family's gate by name, naming as examined only rows read in full (C9). On a corpus no family owns, each marker update goes to the user as a fork. **Report**.
- **Gates beside the steps.** Inventory arithmetic: every inventory path belongs to a unit or a named exclusion. Coverage: count a path as read only where tool evidence shows a full read, and `accept` checks each receipt against the input version its row recorded (C8). Positive controls run on every numeric scan (C4). A decision guard searches the removed lines under `diffs/` for decision markers with the ledger's `search`, and the edited pages for any decided item still stated as open. The closing checks are the linter differential and a net-diff audit that finds a review row for every changed path.
- **Failure handling.** A plan whose tasks cover fewer target paths than the findings name stops the run before Write. The planner gets one re-invocation with the gap listed, and a second miss fails the phase, which the report states. The terminal validator writes only its named set and returns a shortfall report when an upstream phase produced nothing. A dead finder earns one re-invocation, and then its unit is reported unreviewed. A finding whose lenses both failed stays unverified. An aborted writer's paths are reconciled from the diff before any re-dispatch (P4).
- **Stop and ask.** Put the verification scope to the user with the scope and the estimate. Before dispatch, route every write to a marked page or capture to the owning family's gate or to the user, whatever the write changes (C9). A widening from review to fix, a marker advance past the rows read in full, and an item that fails its re-check go to the user. Every decide-class finding and every writer contradiction goes out as a decision packet (P6). Writers keep every recorded decision. Where a source undercuts a decision's premise, the writer adds one sentence saying the premise is worth revisiting.
- **Report.** Build it from the tally block (P6). The opening sentence counts the helpers dispatched, returned, and accepted in each phase. Coverage splits into read in full by tool evidence, claimed by receipt only, only searched, and unexamined, and each unexamined class names the check that would cover it. Findings are counted raised, verified, narrowed, and refuted per lens, split into recall-confirmed and independently surfaced. Each unverified band carries its sample rate, and a zero refutation rate is named as a calibration question. List the paths written, reviewed, repaired, and re-checked, the open items by id, and each hand-off with the rows it names as examined.
- **Cost profile cuts.** A narrower verification scope, a smaller sample of each unverified band, and a lower cap on gap units.
- **Tier notes.** Inline floor: Find and Verify run as separate passes, each closing on its return file, and Review reads the per-file diffs that `diff` wrote. Batch delivery: each wave's lenses go out in the batch after its finders, and a row that returns late is marked as over its bound (P4). Notice delivery: send a unit's Verify rows once its Find return is accepted, and park page writes until the readers return (P5). Where the notice carries no result, batch the read-only roles (P3) and poll the Review wave inside the turn (P4).
- **Family-owned variant**, in `<family_owned_variant>`. When the user names agent_spinner for a knowledge base the wiki family owns, the family writer stays the only writer. The orchestrator runs the scout, Find, the critic, and Verify at its own level, then hands that writer the confirmed list as a scope the user approves. After the writer returns, the orchestrator runs Review and sends every repair back to the family writer as a scope the user approves. It relays the family agent's report as that family's contract requires. The family agent keeps its own checks, and the variant restates none of them. The variant runs on a scope the user states, or once wiki_fix accepts a list of confirmed findings as its scope.
- **Post-run checks.** Unit rows equal the inventory minus exclusions, and each unit has an accepted return with a coverage list. Every write-bound finding has two lens verdicts or an unverified label. Writers equal the distinct target paths, and every changed path has a review row. Every changed marked path has a hand-off or fork row, and each hand-off names as examined only rows read in full (C9). Every premise sentence the plan routed exists in its landed page.

### `artifact-repair.md`: J4, drift repair across many artifacts

- **Trigger.** Per-artifact fan-out. The ask finds which of many specification artifacts, such as tasks, specs, or procedure pages, drifted from the repository, fixes them, and checks the fixes. Signals are items with anchors into the code, status stamps that separate gates own, and completed items beside live ones. Where a shipped family owns the backlog, its contract governs, and every stamp consequence goes to that family's gate by name. That family's contract states what the gate does.
- **Ledger steps.** `init` takes the drift table's drifted rows, with each row's stamps as the owning family reports them. An item fails its check when that check raised a blocking or should-fix finding, whatever its verdict word, and a nit-only item goes to the report. `rows --phase write --from-repair-list` creates one row per item on the repair list (C5). `rows --phase write --from-records` creates one write row per critic finding that needs a repair or a new artifact, and `diff --add-checks` adds its check row. The link-graph validator runs before `close`, and the roster shows a routing or fork row for every changed path recorded as stamped (C9).
- **Phases.** **Write**: a writer repairs each drifted artifact and reads no earlier helper return. Its brief has four parts: what is stale, the tree state to verify, the fix, and what to verify without assuming it is stale. **Check**: a checker reads each repair's diff against its brief, with the writer's return, and goes out as its writer returns. **Critique**: three critics each test the scout's work under one lens (C6), reading the drift table and the net diff and no helper return. One refutes every item the scout called current, one reads recent commits for landed work no item accounts for, and one scans outward from the touched code.
- **Width.** One writer per drifted row and one checker per repair. One remediator per item on the repair list (C5). Three to five critics. One write-and-check pair per critic repair and per new artifact. One advocate per side for each trade-off proposal, such as a merge or a split.
- **Roles and returns.** The writer returns its label and path, what it applied and skipped, brief corrections, judgement calls, the contract clauses its changes touched, a statement that it left the stamp alone, and incidents. The checker returns a verdict (clean or issues) and issues with a severity (blocking, should-fix, or nit). It also reports the anchors checked and those that miss, whether intent was preserved, the stamp consequence, and the fate of each input finding: resolved, refuted with its re-derivation, or silently dropped. The critic returns its lens, findings with evidence, and items confirmed clean with citations. The remediator returns applied, refuted with its span, or routed per finding, plus the minimum edit it made.
- **Adversarial checks.** The repair checker opens from the position that the repair is incomplete or wrong and runs a closed checklist of seven to nine lines. The lines check that the diff matches the writer's report, with unrequested and missing changes listed; every quoted anchor is re-derived; no new defect of the repository's banned classes appears; intent is unchanged; stamps are unchanged and the stamp consequence is stated; the named staleness is gone; and every input finding is accounted for. A trade-off question gets a symmetric stance: one challenger per side, the user's objective in the user's own words, and a status-quo cost beside every proposal (C2).
- **Orchestrator gates, in run order.** **Scout**, before Write: read every artifact and test its anchors, run the gate-scope check, and write a drift table. The table names the method behind each verdict and lists the items judged current, marking those judged on anchors alone. **Lifecycle triage**, before Write: route each completed item to its audit or close-out, or to a new follow-up item, and leave its contract as delivered. Route every write to a stamped target to its owning gate by name, or to the user as a fork, whatever the write changes (C9). **Sibling-surface enumerator**, at the barrier before any contract repair: one helper lists every surface that carries the same contract. **Critic rows and new artifacts**, after Critique: every critic repair and every new artifact (a filing, merge, split half, or repoint) gets its own write-and-check pair. A new artifact starts at its initial lifecycle state, with its inbound-reference map built from the repository root. **Repair round**, after the critic rows and new artifacts. **Terminal validation**, last: one terminal writer runs the linter last and the link-graph validator from the root, and status fields go to the owning family's gate by name (C9). **Report**.
- **Gates beside the steps.** Net-diff attribution maps each changed path to a write row or marks it out-of-band, so the user's concurrent edits are recognised as the user's. Each writer's diff touches only its own path.
- **Failure handling.** Return templates put the verdict first and allow at most one long free-text field, because a return with two overlapping fields can oscillate between them until its retries run out. A failed slot is attributed by label and re-invoked once. The synthesis receives the full item list with states, so it names any missing slugs.
- **Stop and ask.** Surface completed items, stamp consequences, every labelled fork, every deletion of committed content, and every trade-off answer. Quote the governing skill's writer rule in the plan, and state any departure from it in the same sentence as the work, together with the user's permission.
- **Report.** Keep brief corrections, checker findings, and critic findings apart. Give verdict counts from records, and each stamp consequence with the gate or user it went to. Compare the forks returned with the forks relayed, list each filing with its check row, and close with open items by id and yield.
- **Cost profile cuts.** Critics beyond three, and single-artifact panel lenses beyond three, each dropping extra looks at the same work.
- **Tier notes.** Inline floor: write and check run back to back, and the critics share the scout's context, so their confirmations are recall-limited. Batch delivery: waves, with the returned batch as the barrier before the critics. Notice delivery: checks wait on accepted writer returns, run control reads the roster through `status`, and the final wave is polled inside the turn with `accept --wait` (P4).
- **Single-artifact variant**, in `<single_artifact_variant>`, for one artifact repaired over several rounds when no family loop governs it. A panel of three to five lenses over the identical artifact replaces a single first readiness draw, and it includes an interaction lens that derives touch points and searches the code for them. The issue-by-stance list goes to the roster, each row keyed by a slug of the issue text, with one reviewer per stance: one adds proof and one trims. The sibling-surface enumerator runs before any proposal. The verifier reads the gate verdict and every reviewer return by file, with no preference stated, and quotes the issue sentence each decision rests on (C3). Anchored replacements keyed by approved-edit id are applied, then the post-apply delta audit runs (C1). Every deletion of behaviour-bearing content waits for the user. One re-gate runs in isolation with the transcript store off limits, and one refute pass with external-evidence clears tests the final clean result (C2). A further round waits for the user.
- **Post-run checks.** First-pass writers equal the drifted rows, each writer's diff touches only its path, and every repair has a check row. The repair list equals the failing items plus the class-sweep instances. Every changed path recorded as stamped has a routing or fork row, and every new artifact has a check row. Forks returned equal forks relayed plus forks listed as the orchestrator's own decisions.

### `check-only-audit.md`: J7, check-only audit sweep

- **Trigger.** Per-artifact fan-out. The ask sweeps a set of artifacts with an audit and reports what to fix, read-only. Any fix runs later and only on the user's word.
- **Ledger steps.** `init` takes the resolver's artifact list. Every deterministic checker runs through `gate` before dispatch. Findings become ledger records, and `rows --phase verify --from-records` creates one verifier row per finding before any verifier brief exists.
- **Phases.** **Review**: a reviewer reads each artifact, and one reads each comparison cluster, reading no earlier helper return. Per-artifact reviewers carry the depth checks, and cluster reviewers carry only cross-member comparisons. The union of clusters equals the artifact list, singletons receive their neighbours' text, and a cluster above about five members hands its depth checks to per-artifact helpers. **Verify**: a refute-by-default verifier tests each finding, reading that finding's record from the review returns. It works on atomic claims with span-cited refutation, gives a real but low-value finding its own verdict, and runs at no lower depth than the reviewer.
- **Width.** One reviewer per artifact plus one per comparison cluster, and one verifier per finding.
- **Roles and returns.** The reviewer returns findings as atomic claims, a read receipt for every mandated rubric, and what it examined and cleared per criterion. The verifier returns a verdict per atomic claim with its settling span, including the direction of the recommendation.
- **Adversarial checks.** `accept` checks each read receipt against the input version its row recorded, never against the live file. Count a path as read only where tool evidence shows a full read, and report a path claimed by receipt alone as unverified by tool evidence (C8). Pair receipts with the class re-sweep, which is the recall check. A clean result without citations routes back once, and the join keeps dead and clean apart (P3).
- **Orchestrator gates, in run order.** **Scout and deterministic checkers**, before Review: enumerate the artifacts with the repository's own resolver, and run the gate-scope check and every deterministic checker over the whole set. Read the repository's test and coverage model before judging any gap. Write the settled results into the preamble as measured facts, and share them with the user while the helpers run. **Class sweep and recall probe**, after Verify and before any unit is called clean: `rows --phase review --from-records` creates one sweep row per confirmed class, from one of its confirmed findings, and that row covers every unit. Each clean unit chosen for the recall probe gets one probe row from its review record (C8). **Report**: per-unit status lists with counts computed from them, and the fix-or-file fork. **Fix**, in a later run on the user's word: a single writer re-derives each finding and checks each recommendation's direction against the standing rules and the user's latest preference. It re-runs the deterministic checkers, accounts for every removed line, and gets the paired check over the diff. A prior-art check runs before any follow-up task is filed.
- **Gates beside the steps.** The resolver's count equals the inventory. Deterministic checkers run on the full set before dispatch and on the edited files after a fix, and the lint passes after a fix.
- **Failure handling.** A null review leaves its unit unreviewed, and a verifier that threw leaves its finding unverified. Neither counts as clean or refuted.
- **Stop and ask.** The fix-or-file fork and every direction conflict go to the user. Commits and version bumps wait for the user's explicit request.
- **Report.** Count units as clean with citation, clean after the probe, or unreviewed, and findings as refuted, narrowed, or downgraded. Label each survivor from its ledger tag: "survived its verifier, recall-confirmed" where the verifier's brief relayed it. Reserve "confirmed" for a finding surfaced independently or re-derived against the source. Split the confirmations into recall-confirmed and independently surfaced, and close with the fork.
- **Cost profile cuts.** Comparison clusters, which drop cross-member comparisons, and the recall probe on clean units, which drops the direct recall measure beside the class sweep.
- **Tier notes.** Inline floor: reviewers run as separate passes, and the report says verification is recall-limited. Batch delivery: reviewers in one batch, verifiers in the next. Notice delivery: each finding's verifier row comes from `rows` as its review is accepted, and its verifier goes out then. Poll the final wave inside the turn with `accept --wait` (P4).
- **Post-run checks.** Every unit has a state, every clean unit carries citations, and the counts match the lists. Every receipt matched the input version its row recorded, every path counted as read has tool evidence of a full read, and every finding record has a verifier row.

### Selector rows

Add these three rows to the recipe table inside `<selector>`, in the frame's column order. They are the compact rows the routing task's selector budget already counts, which keeps `SKILL.md` within its byte limit.

```markdown
| Repair many artifacts against the tree | `artifact-repair.md` |
| Audit many artifacts, changing nothing | `check-only-audit.md` |
```

### Per-recipe static checks
